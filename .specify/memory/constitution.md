# 四格漫畫任務｜我的漫畫冒險憲章

## 核心原則

### I. 簡潔與目的導向

每項功能必須解決一個明確的學生學習需求、教育者需求或產品問題，並避免未經證實的抽象化。實作必須採用符合需求的最簡單、可維護方案。只有在多個功能或程式路徑已證明有共同需求時，才可引入共用基礎設施。

此原則讓產品聚焦於國小四至六年級學生的學習體驗，避免增加短期複雜度及不必要的操作負擔。

### II. 測試先行開發（不可妥協）

行為變更必須先以可執行測試或驗收條件描述需求，並在開始實作前觀察到測試失敗。實作使該測試通過後，才可視為完成。測試必須涵蓋成功情境、相關失敗情境及邊界條件。

測試是可執行的規格，可防止回歸並驗證成果符合已批准需求。

### III. 整合與使用者體驗驗證

跨越元件、資料或服務邊界的變更必須包含受影響公開契約的整合驗證。凡涉及使用者操作、導覽、無障礙或狀態轉換的流程，必須以 UI 或互動層級驗證。學生與教育者的主要使用流程必須依已批准的 UX/UI 規格進行驗收。

整合及體驗驗證可避免個別元件雖然通過檢查，整體產品流程仍無法使用。

### IV. 可靠性、安全與隱私

系統必須明確處理失敗，不得以成功結果掩蓋錯誤。日誌、錯誤訊息及診斷資訊必須提供足以識別受影響操作的脈絡，且不得揭露憑證、學生個人資料或其他敏感資訊。信任邊界的輸入必須經過驗證，資料與服務存取必須遵循最小權限原則。

產品僅可在具明確且經批准的教育目的時收集學生個人資料；規格必須說明資料用途、存取範圍、保存及刪除方式。涉及學生資料或兒童安全的決策必須由成人教育者或獲授權的成人決策者審閱批准。

明確的失敗處理、資料最小化及成人審閱，可降低誤導使用者及不必要暴露兒童資料的風險。

### V. 相容性與可維護演進

公開介面及持久化格式必須有文件說明，並維持向後相容，除非變更已獲批准且附有遷移與棄用計畫。破壞性變更必須遵循語意化版本原則。命名、模組邊界及資料結構必須遵循已確認的專案慣例。

明確的相容性規則可讓產品與資料格式的演進可預期。

## 補充限制

- 使用者需要閱讀、審閱、批准或操作的文件必須使用台灣繁體中文；程式語法、識別字、正式 CLI 指令、技術名稱及檔案路徑可使用英文。
- 面向學生的內容、文字及互動必須適合國小四至六年級學生；涉及學習目標、學生資料或兒童安全的重大產品決策必須取得成人教育者或獲授權成人的批准。
- 專案必須遵循已批准的技術棧；除非變更另行取得批准並記錄影響，否則不得擅自更換技術棧。
- 應用程式碼不得提交秘密或憑證。外部相依套件必須有具體需求依據；標準平台已有等效能力時，宜優先採用標準能力。
- 除非正常建置或發佈流程確實需要，否則不得將產生的檔案提交至版本控制。
- 在既有 Repository 中進行變更前，必須先唯讀確認工作目錄、Git 根目錄、分支、HEAD、已追蹤與未追蹤檔案及未提交變更，並檢查既有規格與工作區指引。
- 必須保護既有 `.git/`、`.github/`、`.specify/`、`.vscode/`、`specs/` 及其他專案文件；不得以 scaffolding 覆寫、刪除或重建既有內容。若專案狀態或既有規格與工作要求衝突，必須停止並請求確認。
- 未獲明確授權前，不得執行破壞性 Git 操作、提交、推送、建立遠端 Repository 或部署。

## 開發流程

- 專案必須採用 GitHub Spec Kit 規格驅動開發。產品實作前，相關 Specification、UX/UI Design 及 Technical Plan 必須完成審閱與批准；未獲明確授權前，不得開始產品實作或部署。
- 每項變更必須說明受影響需求及驗證方式。行為變更必須遵循測試先行原則；使用者流程、跨元件契約或安全敏感行為必須加入相應的整合或體驗驗證。
- Pull Request 必須通過相關自動化檢查，並清楚說明使用者可見影響及技術影響。審閱者必須確認需求涵蓋、測試品質、安全敏感行為、向後相容性及本憲章遵循情況。
- 複雜度必須在實作或變更紀錄中說明理由。受影響的文件或範例必須在同一變更中更新，並遵循本憲章的語言政策。
- 每一階段必須保留人為審閱與批准點。若現有工作區尚未完成必要的 Repository 或規格盤點，必須先完成盤點；Spec Kit 尚未初始化時，必須先提出安全方案並取得批准，不得自行初始化。

## 治理

本憲章優先於與其衝突的非正式慣例。修訂必須記錄變更內容、影響及必要的遷移方案，並在寫入前取得批准。每次修訂必須更新同步影響報告；該報告供審閱使用，提交憲章時必須移除。

憲章版本必須遵循語意化版本：

- MAJOR：不相容的治理原則變更、刪除或重新定義。
- MINOR：新增原則或章節，或實質擴充既有治理要求。
- PATCH：不改變治理意義的澄清、文字修正或錯字修正。

所有 Pull Request 與審閱必須驗證符合現行原則。例外必須明確記錄適用範圍、理由及期限，並在合併前取得批准；涉及學生資料或兒童安全的例外另必須取得成人教育者或獲授權成人的批准。
